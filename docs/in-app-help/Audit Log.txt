Audit Log

  What it is
  The Audit Log is an append-only record of every significant action taken in LicenseTrack. It tells you who did what, when, from where, and what changed — giving you a complete history for compliance, investigation, and accountability purposes.

  How it works
  Every write operation across the system appends a row to the audit log in the same database transaction as the underlying change. This means an audit entry always exists when the change exists, and never exists for a change that was rolled back.

  Each entry records:
  - Timestamp — when the action occurred (UTC).
  - Actor — the email address of the user who performed the action.
  - API token — for machine-to-machine requests, the token's numeric ID and name are recorded in dedicated fields (actor_token_id and actor_token_name). Human-session requests leave these fields empty.
  - IP address — the remote address of the request.
  - Action — a dot-separated code identifying the event type, such as license.created, user.role_changed, or system.backup_restored.
  - Target — the type, ID, and a human-readable label of the record that was affected (for example, "license" / "42" / "LT-2024-00017 — Adobe Acrobat").
  - Detail — a field-level diff for update events, showing old and new values for the fields that changed. Sensitive fields such as passwords and OIDC client secrets are never included in the diff.

  Viewing the log
  The Audit Log is accessible from the Admin page. It is paginated, showing up to 200 entries per page. The UI exposes date range filters, a free text search box, and category/action filters. The free text search matches against the target label, the detail text, the actor email, or the API token name.

  The audit log API also supports more specific filters for integrations and troubleshooting:
  - Actor email — partial match against the email address of the user who performed the action.
  - Action type — partial match against the action code (for example, entering "license" will match license.created, license.updated, and license.deleted).
  - Date range — from and to dates (inclusive) on the timestamp.
  - Free text search — matches against the target label, the detail text, the actor email, or the API token name.
  - API token ID — exact match on the numeric token ID to isolate all activity from a specific integration.

  Exporting
  The current filtered view can be exported as a CSV. The export applies the same filters as the on-screen view and returns all matching rows with no pagination limit. The CSV contains columns for timestamp, actor email, actor token ID, actor token name, IP address, action, target type, target ID, target label, and detail.

  Automatic pruning
  The audit log is pruned by the background scheduler according to the retention period configured in global settings. The default retention period is 90 days. Admins can choose a different supported retention period in the Operations settings. The scheduler prunes entries older than the configured threshold on startup and once per day.

  Key concepts
  Action code — a dot-separated identifier for the event type, structured as object.verb (for example, license.created, settings.updated, system.backup_restored).
  Actor — the user whose session performed the action. If the user has since been deleted, the email address is retained in the audit entry rather than nulled.
  Detail diff — the per-field record of what changed in an update event, formatted as "field: old_value → new_value". Fields excluded by default include id, created_at, updated_at, created_by, and the renewal-chain fields renewed_to_id, renewed_from_id, lifecycle_status, coterm_predecessor_ids, and coterm_from_ids.
  Retention period — the number of days of audit history to keep; entries older than this are deleted by the background scheduler.

  Who can use it
  All admin users can view, filter, and export the audit log. Break-glass-only restrictions apply to recovery-sensitive actions (such as database restore), not to routine audit access.

  Things to know
  - The audit log records the actor's email address at the time of the event. If an admin later changes a user's email, the old email remains in entries logged before the change. This is intentional — the log is an immutable record of what happened, not a live view of current user state.
  - IP addresses are recorded from the request as seen by the FastAPI process. If LicenseTrack is deployed behind a reverse proxy, the logged IP will be the proxy's address unless the proxy is configured to forward the real client IP.
  - The detail diff intentionally omits sensitive fields (passwords, secrets) and housekeeping fields (timestamps, internal IDs). An update event with no meaningful field changes produces no detail entry.
  - The CSV export uses the same filters as the on-screen view and has no row limit — a filter-free export on a large audit log will include every row and may be slow to generate.
  - Audit log pruning is handled by the same background scheduler as notifications and backups. If the scheduler is not running (for example, in a development environment with manual process management), no pruning will occur even if a retention period is configured.
