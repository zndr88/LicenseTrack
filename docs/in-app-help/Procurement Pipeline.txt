Procurement Pipeline

What it is
The Procurement Pipeline is the end-to-end workflow for turning a planned software purchase into active license records. It keeps sourcing requests, quote documents, purchase orders, invoice documents, and resulting licenses connected so nothing falls through the cracks between "we intend to buy this" and "we own this."

How it works
The pipeline runs in three connected stages.

The first stage is Sourcing. A sourcing request is the parent procurement container for quote-stage work. It can hold one or more license line items, and each child line item represents a license to buy or renew. This means a single supplier quote or buying motion can contain multiple license lines without duplicating parent-level context.

On the Sourcing Overview page, request rows can be expanded to show their license line items. The parent request table shows request-level evidence inline, including uploaded quote downloads in the Quote column. The request row owns request-level actions such as quote upload, conversion to pending order, and cancelling the full request. The child line rows own item-level actions such as edit, delete, and coterm merge selection. Quantity displays use your personal number-format setting.

The History button on Sourcing Overview opens a second table below the active sourcing table. This history table contains converted and cancelled sourcing requests, has its own search box, and is read-only: users can download quote evidence and inspect request and line details, but cannot add, edit, merge, convert, or cancel history rows. Converted sourcing rows keep their request id and line ids. When a converted sourcing request is linked to a pending order, View PO opens the matching active or historical pending order; when several POs are linked, expand the sourcing request and choose the PO from the relevant line.

Quote documents are uploaded against the sourcing request. They remain tied to the sourcing origin during sourcing and pending-order work, then become pending-order-scoped procurement documents when the pending order is converted into licenses.

If multiple renewal line items need to share the same end date in a coterm arrangement, the relevant sourcing items can be merged. The merge creates a coterm renewal line with a combined quantity while preserving predecessor license references used later during license conversion.

When procurement is ready to raise a PO, the sourcing request is converted to a pending order. All child sourcing line items move under that pending order as PO line items. The sourcing request and its line items are marked converted, preventing the same sourcing request from being progressed again.

The second stage is Pending Orders. A pending order is the PO-level parent container. It has one or more nested line items that came from sourcing or were added directly during the pending-order phase. Pending Orders is a continuation of the sourcing work, so line items remain actionable until the PO is fully converted into licenses.

On the Pending Orders page, the PO parent table mirrors the sourcing overview layout: PO number, supplier, item count, total PO value, created date, purchase-order document, status, and actions. Uploaded PO documents are downloaded from the parent row's PO column and can be deleted while the pending order remains editable. The parent row owns PO-level actions such as edit, purchase-order document upload, convert, and cancel. Expanded child rows own line-level actions such as quote download, edit, and delete. Users can also add forgotten license lines during this phase. Quotes remain owned by the originating sourcing request and are visible from the pending-order line when that line came from sourcing. Quantity displays use your personal number-format setting.

The History button on Pending Orders opens a second table below the active pending-order table. Converted and cancelled POs are searchable there without cluttering active PO work. History rows are locked against ordinary PO and line edits, but they keep PO documents, carried-forward quote evidence, invoice evidence, order ids, line ids, and conversion references. If one license was created from the historical order, View License appears on the parent row. If multiple licenses were created from the order, expand the order and use View License on the individual line.

The Pending Orders CSV export is flattened for spreadsheet and reporting use. Each pending-order line item becomes its own CSV row, and the parent PO metadata is repeated on every row for that PO. Pending orders with no line items are still exported as one row with blank line-item columns so the parent PO remains visible in reporting. The exported columns include PO number, supplier, status, created date, PO total value, currency, PO line number, publisher, description, quantity, estimated unit price, and estimated line total. PO number acts as the visible relational identifier across rows, while the line number distinguishes item order inside the PO.

Sourcing and Pending Orders use the same rectangular status badge treatment as the License Registry and Renewal Workbench. Sourcing-stage work is shown with the blue sourcing badge; pending-order-stage work is shown with the purple pending badge.

The third stage is License Conversion. When the purchase is complete and the licenses are ready to enter the registry, the pending order is converted. A single-line PO can be converted through the single conversion flow. A multi-line PO can be batch-converted so each line item becomes its own active license record.

During multi-line PO conversion, users can copy shared PO-level fields from the first item into the remaining items. This copies PO number, contract number, invoice number, contact email, supplier, cost centre, currency, and budget owner email. The copy action can overwrite values on other items, so each license should still be reviewed before confirmation. Conversion notes remain editable per line and preserve relevant PO-level, sourcing-line, and predecessor-renewal context instead of silently discarding it.

At conversion time, users can optionally upload the supplier invoice next to the invoice number. LicenseTrack stores quote, purchase-order, and invoice files once against the pending order. Every license created from that pending order can see those procurement documents. A later separate pending order with the same PO number does not inherit those files automatically. Renewal lines use their predecessor license references to mark old licenses as renewed and create successor licenses.

After conversion, admins and editors may still add supporting documents to a license or procurement record as an evidence amendment. This is intended for late invoices, entitlement certificates received after procurement, legacy imports, shadow IT cleanup, or purchases discovered outside the standard sourcing workflow. The amendment is part of the historical record; it does not reopen the converted sourcing or pending-order workflow.

If a converted line is a maintenance license, the user must explicitly choose its parent. The parent can be an existing active perpetual, OEM, or freeware/open-source license, or an eligible line being converted in the same pending order. LicenseTrack does not auto-link maintenance by PO number.

Once conversion completes, the pending order status becomes converted and the resulting licenses appear in the License Registry. Converted pending orders and their line items are locked against further item-level edits and move to the Pending Order History view.

Each resulting license stores two procurement milestone timestamps. Request Date is copied from the sourcing item creation time when a source line exists. Purchase Date is copied from the pending order creation time. The timestamps remain visible under License Details > Key Dates & Contract after conversion. The License Details > History section also shows a Procurement Trail when source records are available. The trail links back to the originating sourcing history line and pending-order history record, shows the relevant supplier, description, value, status, and evidence counts, and lets users move from a converted license back through the historical procurement steps. Admins and Editors can edit Request Date and Purchase Date later when enriching imported or legacy licenses. During database migration, historical Purchase Date values can be backfilled from the linked pending order. Historical Request Date values are backfilled only when a pending order has one unambiguous source line; multi-line historical orders are left blank rather than guessed.

Key concepts
Sourcing request - the parent quote-stage procurement container. It holds supplier/contact/notes context, quote documents, and one or more sourcing items.

Sourcing item - a child license line inside a sourcing request. It represents one planned license purchase or renewal.

Quote document - a document uploaded against a sourcing request. Quote documents become pending-order-scoped procurement documents when the pending order is converted.

Purchase-order document - a document uploaded against a pending order. It is stored against that pending order and is visible from every license created from it.

Pending order - a PO-level parent container that holds one or more line items after sourcing conversion or direct PO item entry.

Pending order line item - the continued sourcing/license line while a PO is awaiting fulfillment. It can still be edited, deleted, or supplemented before final license conversion.

Invoice document - a document uploaded during pending-order-to-license conversion. It is stored against that pending order and is visible from every license created from it.

Coterm merge - combining multiple renewal sourcing items into one coterm renewal line so the resulting license renewal can align predecessor licenses to a shared period.

Convert to pending order - the action that moves a sourcing request and all of its child line items into a pending order.

Convert to license - the action that turns a pending order into one or more live license records.

Batch conversion - converting multiple pending order line items into individual license records in a single step. Maintenance lines in a batch must point to an explicit parent, either from existing licenses or from another line in the same conversion.

Procurement milestones - Request Date and Purchase Date snapshots stored on resulting license records so sourcing and PO history remain visible after conversion.

Sourcing history - the read-only converted/cancelled sourcing table shown below active sourcing when History is enabled. It keeps request ids, line ids, quotes, notes, and links to related pending orders.

Pending order history - the read-only converted/cancelled PO table shown below active pending orders when History is enabled. It keeps order ids, line ids, PO documents, invoices, quote context, and links to resulting licenses.

Procurement trail - the linked history shown in License Details > History. It connects the active or renewed license back to the source sourcing request/item, the pending order, and the procurement evidence bundle when those records exist.

Who can use it
Admins and Editors can create, edit, merge, upload quote documents, convert sourcing requests, manage pending order line items, upload invoices during conversion, and convert pending orders into licenses. Viewers have read-only access where their role and department scope allow it.

Ownership notes
The sourcing stage is owned by sourcing models, schemas, routes, and sourcing_service. SourcingRequest is the parent container; SourcingItem is the child license line; SourcingQuoteDocument stores quote metadata.

Pending-order CRUD and line-item management are owned by pending_order_service and the pending orders route. This includes adding, editing, and deleting pending order line items before conversion.

Pending-order CSV export assembly is owned by pending_order_export_service. It exports a flat, one-row-per-line-item dataset and repeats PO-level fields per row rather than grouping child items into combined cells. Orders without line items are represented by a single parent-only row with blank item fields.

Pending-order-to-license conversion is coordinated by pending_order_conversion_service. The coordinator loads and validates the pending order, chooses the conversion path, manages transaction order, updates pending-order and sourcing-item statuses, writes audit events, and returns the conversion response. Focused conversion helpers own the risky subflows: conversion/license_converter.py creates new purchase licenses, conversion/maintenance_linker.py resolves maintenance parents and creates maintenance children, and conversion/pending_order_status.py owns status transitions. Renewal successor and coterm behavior is delegated to renewal_orchestrator.

Invoice validation/write and quote-document carry-forward are owned by procurement_document_transfer_service. pending_order_conversion_service validates invoice uploads before any DB mutation, commits license/status changes first, then writes invoice and quote procurement document rows after the conversion transaction succeeds. If the document copy fails after the conversion has committed, the pending order's evidence_transfer_status is set to "failed" and the error detail is recorded. The transfer can be retried via POST /api/pending-orders/{id}/retry-evidence-transfer (Admins and Editors only), which re-runs the quote document copy and is safe to call multiple times — existing documents are not duplicated.

File persistence is delegated to storage helpers. Route modules should stay thin: they handle auth, request parsing, response shaping, and audit log wiring while delegating business rules to services.

Things to know
- Sourcing requests and sourcing items become converted after they are moved into a pending order and remain available from Sourcing History.
- Cancelling a sourcing request moves it and its child line items to Sourcing History. For renewal lines, the predecessor license's renewal process is cancelled when no other sourcing line still references it.
- Pending order line items remain editable until the pending order is converted into active licenses.
- Converted and cancelled pending orders are locked against item-level edits and appear in Pending Order History.
- Sourcing and pending-order history tables are reference views. They preserve old context without reopening the workflow.
- Click-through links use stored database relationships, not PO-number text matching. A reused PO number does not merge unrelated history.
- Pending orders with no line items are included in the CSV export as parent-only rows.
- Quote documents belong to sourcing requests until conversion, then copy once into the pending order's procurement document set. If that copy fails (for example due to a storage error), the pending order is still marked converted but its evidence_transfer_status is set to "failed". The background scheduler automatically retries failed and stuck transfers every 60 seconds, up to 5 attempts. After 5 failed sweep attempts the order is marked "escalated" and a po.evidence_transfer_escalated audit event is emitted; manual intervention is then required to resolve the transfer. Admins and Editors can also trigger a retry immediately using POST /api/pending-orders/{id}/retry-evidence-transfer without re-converting.
- Quote, purchase-order, and invoice files are shared by licenses created from the same pending order, not by PO number alone.
- Maintenance conversion requires an explicit perpetual/OEM/freeware parent selection. The parent can be an existing active license or another eligible line in the same pending order conversion.
- EULA, entitlement, and other documents remain license-owned unless explicitly changed later.
- Documents added after conversion should be treated as evidence amendments: useful for late or discovered evidence, but separate from the original conversion event.
- You can export both the sourcing list and the pending orders list to CSV at any time.
